# DeathRun Classic26 engineering playtest

The playtest world generated by this fork is an original engineering fixture. It does not redistribute Hive or third-party downloaded maps.

## Required
- Paper 26.2
- Java 25
- WorldEdit 7.4.5

## Run a match
1. Put the built DeathRun JAR and WorldEdit in `plugins/`.
2. Start Paper.
3. As an operator run `/dr playtest create`.
4. Run `/dr playtest verify` and confirm the structural audit passes.
5. Run `/dr map trace start classic26-playtest` before anyone joins.
6. Players run `/dr join classic26-playtest`.
7. With at least two players run `/dr start classic26-playtest` to bypass the normal 11-player Classic threshold.
8. Test Runner lives/checkpoints/strafe, Death navigation/activation, all 17 included traps, finish timing, and state restoration.
9. Run `/dr map trace stop classic26-playtest`.

Generated world: `deathrun_playtest`.


## What `/dr playtest verify` checks

The verifier is deliberately stricter than a simple map load. It checks the generated engineering fixture for:

- 20 Runner spawns and 2 Death spawns
- max 22 / required 11
- 4 checkpoints with points 3 / 7 / 10 / 13 and the final checkpoint marked as Finish
- a start barrier with a matching restore snapshot
- all 17 expected Classic26 trap implementations
- valid trap buttons and target regions bound to the playtest world
- valid Runner, Death, checkpoint and barrier world bindings
- a live arena runtime for `classic26-playtest`

CI runs this audit once immediately after creating the fixture and again after a full Paper restart/deserialization cycle.


## Human acceptance trace

For the final two-client acceptance pass, enable the trace before joining:

```text
/dr map trace clear classic26-playtest
/dr map trace start classic26-playtest
/dr map trace status classic26-playtest
```

The trace records game-state transitions, joins, role assignment, successful Classic strafes,
checkpoint results, deaths/lives/elimination, successful trap activations, booster use, finishes,
leaves, and the next-tick player-state recovery result.

After the test:

```text
/dr map trace stop classic26-playtest
/dr map trace acceptance classic26-playtest
```

The private report is written to:

```text
plugins/DeathRun/research/classic26-playtest-playtest-trace.log
```

This file is intentionally not committed to the public repository. It is the preferred artifact to
attach when a real-player acceptance step fails because it preserves the internal state transitions
without requiring screenshots for every event.


### Acceptance verdict

`/dr map trace acceptance classic26-playtest` analyzes the trace instead of requiring manual log review.
The strict engineering-fixture verdict requires evidence for:

- at least two joined players and both Runner/Death role assignment
- PLAYING, ENDING and post-round WAITING transitions
- successful Left, Back and Right Classic strafes
- Death Navigator Previous/Next, successful Trap Jumper and hotbar Activate
- at least one successful physical trap-button activation
- every configured checkpoint and every configured trap index
- one non-eliminating death and one zero-lives elimination
- a first-place finish followed by a remaining-time clamp of at most 60 seconds
- successful player snapshot restoration
- an active-session disconnect followed by reconnect/recovery with no pending snapshot

The trace can span multiple rounds, so the finish path and zero-lives elimination path do not have to
be forced onto the same Runner in one two-player round.

## To Bee multiplayer acceptance

Status: human acceptance remains outstanding. CI trap activation and synthetic
trace tests do not substitute for client gameplay.

Use the production setup in README first. With the map idle, run readiness and
fingerprint and retain the fingerprint for the same imported world. Do not run
bootstrap, runtimecheck, restore or reload during client acceptance.

Before either client joins:

```text
/dr map trace start to-bee-or-not-to-bee
/dr map trace status to-bee-or-not-to-bee
```

Starting the trace truncates the previous report. Start it once and keep it
running across the following rounds. Save any previous report before starting.

Each client records their pre-game inventory, armor, offhand, XP, health/food,
location, game mode and flight state for a visual comparison after leaving.
Both clients join with `/dr join to-bee-or-not-to-bee`; an operator can use
`/dr start to-bee-or-not-to-bee` below the normal 11-player threshold.

| Round | Runner actions | Death actions | Evidence to retain |
| --- | --- | --- | --- |
| Finish and controls | Use all three strafes; confirm independent cooldowns; die once without elimination; traverse all five intermediate checkpoints and finish | Use Previous, Next, Trap Jumper and hotbar activation; activate a physical button; exercise every configured trap across rounds if needed | All six configured gates and 23 trap indexes; +2 Lives at normal CPs; first finish at >60 seconds remaining clamps to 60; ENDING then WAITING |
| Elimination | Start with 2 Lives; die twice before gaining checkpoint lives | Observe eliminated Runner can no longer participate | Non-eliminating death followed by zero-lives elimination; restored pre-game state |
| Disconnect | Disconnect while PLAYING, then reconnect with the same account | Observe session cleanup; allow the round to finish | DISCONNECT state=PLAYING, then same player's RECONNECT_RECOVERY pendingAfter=false; visually restored state |

Rejoin before each additional round and keep the trace enabled. Allow a natural
finish/reset in at least one round. For emergency cleanup use
`/dr stop to-bee-or-not-to-bee`; an aborted run does not replace the finish test.

After all clients have recovered and the map is idle:

```text
/dr map trace stop to-bee-or-not-to-bee
/dr map trace acceptance to-bee-or-not-to-bee
/dr tobee readiness <world>
/dr tobee fingerprint <world>
```

Keep `plugins/DeathRun/research/to-bee-or-not-to-bee-playtest-trace.log`, the
PASS/MISS output, both clients' restoration observations and the final
fingerprint. The fingerprint should equal the pre-test value. Keep player
reports private.

A reset only counts when ENDING is followed by WAITING in consecutive STATE
events; ordinary gameplay/log events between them are allowed. Recovery only
counts after an earlier PLAYING disconnect for the same named player. A lobby
disconnect, recovery logged before disconnection, or another player's recovery
cannot satisfy that check.

The analyzer checks event coverage, not every numeric rule or the appearance of
the world on clients. Confirm Lives, cooldowns, finish timing, trap visibility,
route continuity and restored items manually even when the verdict is PASS.
A PASS is recorded evidence from this test session, not proof of full-room
22-player capacity or a completed human test performed by CI.
